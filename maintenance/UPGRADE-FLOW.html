02 / LOCALIZATION LOOP

翻译不是“生成中文，然后盖章”

上游来源、新中文、审查声明、机器契约和候选摘要是不同对象。先检查内容，再记录新的审查绑定，最后做全量检查与重新冻结。

纠正前面讨论中的执行顺序：译文或 source 已经变化时，旧 catalog 摘要通常会失效。不能要求完整 localize.py check 在 record 前就通过；应先做不依赖旧摘要的针对性机器检查与语义审查，再 record，之后全量 check。S3
LOCALIZATION_REQUIRED 的受控恢复不编辑冻结区
前置基础工作

先补共享 checker

普通枚举、布尔值、执行字面量及缩进围栏的漏检，应在稳定基线中修复，再让 Skill 使用。

不会因此取消 AI 复核

主体、禁止、数量、等待条件等自然语言含义，不能靠 token 相等证明。

reviewer 要说实话

AI 新补译应记录实际 AI 审查标识，不沿用旧的 User-approved；同一模型复核不是独立模型证明。

未变内容保持不动

不因上游 commit 改变就全量重译，也不为了“统一”回写已有业务文档。

S2 S3 S7 S10

程序检查保护什么

结构、命令、文件路径、标识、确定属于机器语义的值和执行片段，以及来源／译文的准确绑定。

应按“可执行内容”和“自然语言示例”分类，不能退回到全部反引号／围栏一律禁止翻译。

AI 复核保护什么

谁负责什么、必须或禁止做什么、什么时候等待／停止、能写哪些文件、数量限制及英文输入兼容。

具体语义无法确定时停止；不能用“改动小”或“测试绿了”代替来源审查。

03 / SHARED DEPENDENCY

为什么 Skill 不会替代 machine_contract？

下面是实际实现中的调用关系。上层从人工命令换成 Skill 编排，不会让下层的校验职责消失。S2 S3 S4 S5

重点：build 与 verifier 再次调用同一 checker，能保证生成／交付链一致，却不会凭空消除该 checker 的共同盲区。独立 CLI baseline 主要证明英文来源与适配的等价，不是对任意中文语义的另一份独立证明。S5

ARCHITECTURE

复用的是职责与契约

保留 machine_contract(text) 及现有验证路径。为补漏检，可以有限拆分解析辅助函数、改进内部识别，但不能把已批准的呈现规则改掉。

这属于“先修工具，再让 Skill 使用工具”，不是“未来写 Skill 时再次做一遍同样修复”。

SCOPE

不新建第二套检查真相

不要在 Skill 目录复制 localize.py 或另造放宽版 checker。Skill 调用当前检出的维护工具，记录其准确基线。

需要更改校验规则时，结束本次自动升级，进入独立维护修复工作包并重新验证。

已补齐的 machine-contract 最小反例回归

基础修复已把这些合成反例加入回归：机器值变化必须被预检拒绝，同时既有合法中文呈现继续通过；这仍不等于证明任意自然语言语义等价。

合成修改当前预检结果保护方式
状态：`PASS` → 状态：`FAIL`拒绝机器枚举及其上下文。
sh 围栏中 exit 1 → exit 0拒绝Shell 可执行行与返回码。
{"enabled": false} → {"enabled": true}拒绝结构化 key/value 关联，不只统计 token 数量。
缩进围栏 sh → python，正文不动拒绝／结构检查真实 fence 结构、类型与机器片段。

这不是把“所有英语”锁死

目标是拦截真实机器语义变化，同时让现有 canonical 中文标题、固定响应、自然语言示例继续有效。即使这些反例全部被挡住，也不能宣布已经证明任意翻译语义等价。

04 / STATES, WRITES & EVIDENCE

每个状态到底意味着什么？

区分升级器 record、verifier 报告和 Git／发布事实，不再用一个“PASS”覆盖整条链路。S2 S5 S8

状态／结果来源意味着什么不意味着什么
PREPARING升级器正在生成候选，最终记录可能因错误而保留。不是可用的新版包。
LOCALIZATION_REQUIRED升级器本地化相关错误；需进一步读实际原因。不保证仅翻译即可修好，不授权改 checker。
BLOCKED升级器候选建立后发生阻塞；保留现场。不能通过手改 status/digest 恢复。
CANDIDATE_READY升级器构建成功，候选内容与摘要已记录。不代表 verify 已通过，不代表源分支已升级。
PASSverifier result.json本次完整工程检查通过，绑定准确摘要。不代表任意中文语义或模型真实执行完全正确。
ACCEPT_CHECK_PASSaccept --check接收前检查通过；没有提交。不是正式 ACCEPTED。
ACCEPTED正式 acceptdetached 候选被创建为本地 Git 提交。没有自动 push / merge / tag / Release。
“工程验证通过的候选”sdlc-maintain-upgrade 总结AI review + 完整验证 + 摘要一致的派生结论。不是另一个新增的升级器状态；record 仍可能是 CANDIDATE_READY。
前置失败可能没有 record。仓库不干净、输出路径不合法、命令 inventory 改变等，有些检查发生在候选创建之前。Skill 不能假设每次报错都有一个可供 resume 的候选，更不能凭空创建 BLOCKED JSON 冒充工具记录。

另行授权的接收／交付准确候选提交、短期升级分支、维护文档收尾及其最终证据。默认不动 main、镜像、tag 或 Release；不能覆盖并发新提交。

版本变化已由 prepare 负责

当前政策为 <upstream>-sdlc.<n>。目标上游 package version 变化时，候选产品版本自动变为 <new>-sdlc.1；同上游的本地迭代号仍需维护者显式处理。

例如目标确认为 1.0.6，则候选版本为 1.0.6-sdlc.1。这是候选元数据，不等于已经发版。S2 S8

维护文档不能穿透冻结区

prepare 不会自动修正所有维护文档中的当前版本／SHA。AI 不应在只允许本地化编辑的候选里直接修改 docs/**。

第一版先输出待同步清单；正式接收后再完成文档收尾，并为最终字节重做验证。不为这件事新增一套候选编辑协议。S2 S8

完整升级的“完成”分层

候选构建就绪→候选验证完成→维护者接收→文档收尾 + 最终 CI→按授权合并／发布→客户端实际确认

默认 Skill 只完成前两层并输出差异。不能把 BUILD.json 更新、ACCEPTED 或一次工程 PASS，泛化为所有层级都完成。

在线与 patch：只是交付渠道不同

准确最终版本与证据→授权分支普通推送→读回 SHA + 对应 CI

网络、权限或提交身份无法满足时，才改交准确基线 patch／bundle；须包含新增文件及权限变化，实际试应用并比对结果。若部分提交已成功，补丁针对最后确认的远端 SHA，而不是重复全量修改。

验证失败不能靠“改成 patch”降级成通过。
