# 拆分规则

## 拆分单位

将一个交付范围分成至少两个分别推进的后继范围。每个后继具备明确目标、范围、可说明的验收、已知依赖和后续工作。

允许后继之间存在依赖。分别推进不等于技术上完全无关，也不意味着可以任意独立上线。
优先依据用户结果、可验收能力和明确的分批交付目标划分；不按前端、后端、数据库、测试或任务数量平均切割。
若用户只想调整任务先后、最终仍共同验收交付，先说明保留一个需求可能更合适。

## 从已有信息开始

原始文字与项目画像可形成候选边界和输入简报。技术独立性、工期与发布能力尚未分析时，保留为待确定事项。
已有 SPEC、PLAN、TASK 时，利用已有事实细化边界；不把文档较多当成阶段已经通过。
已有实现时，再读取 [材料与实现承接](implementation-carryover.md)。

## 建立原范围清单

逐项读取并登记：

1. 业务目标、用户、用户故事及可观察结果。
2. 功能、非功能约束、异常和失败路径。
3. 成功标准、验收场景及跨范围的整体判据。
4. 接口、数据、共享技术决策与适用前提。
5. 已有任务、完成声明和已有实现。
6. 未决问题、明确排除项和已确认取消项。
7. 附件、检查清单、历史验证与项目公共约束。

保留原有 FR、SC、US、T 等稳定编号。没有稳定编号时，只建立本次 CUT 局部条目号，不改原文。
引用应包含来源需求、文件与条目；行号引用绑定文件摘要。逻辑条目号不必是 HTML 锚点。
列出其他来源文件并说明是否适用；不能因为工具只认识 spec、plan、tasks，就忽略其他业务附件。

## 为每项原始义务安排去向

| 处置 | 要求 |
| --- | --- |
| 分配给一个后继 | 说明承接目标、材料位置和后续工作 |
| 多后继共同适用的约束 | 明确各自责任，说明为何共享 |
| 已存在的公共基础 | 引用真实实现或约束及适用条件 |
| 保留未决问题 | 明确后继归属、影响和下一步 |
| 用户已确认取消或原本排除 | 保留决定来源，不自行裁定 |

延期必须有承接范围，不能记为排除。不能以合理假设偷偷决定会改变需求边界的待定业务。
如果一个原任务覆盖 A/B，应拆出具体义务，或明确一个建设责任并登记其他需求的依赖；相似标题不足以证明等价。

## 共享建设与共同约束

共享建设指需要做一次、供多个后继使用的实现或契约。给它一个明确执行责任，其他后继引用其结果并承担各自集成验证。
共同约束指多个后继都必须遵守的要求，例如授权检查、数据隔离和兼容条件。它可以映射到多个后继，分别落实本范围。
不要把共同约束误判为重复实施；也不要通过多个目标映射，让两边各自建设同一份基础能力。
已有共享实现无需为了拆分再制造一个基础需求；按实际缺口决定归属，不自动增加第三个需求。

## 依赖与交付顺序

| 类型 | 含义 | 处理 |
| --- | --- | --- |
| 实施前置 | 必须先有代码、数据、接口或契约才能继续相关实施 | 说明前置成果与缺失影响 |
| 发布前置 | 必须先部署某版本、完成迁移或满足运行条件 | 说明发布约束 |
| 建议顺序 | 业务优先级或排期偏好 | 不冒充技术强依赖 |

显式依赖必须有原因。按 [输出契约](output-contract.md) 分类型检查前置关系；不要将建议顺序或当前代码调用图混成同一张硬依赖图。
当前代码循环调用、共享文件或实现耦合属于现状分析，不直接等同于后继工作前置循环。
A 要提前交付时，检查其是否需要尚未交付的 B。需要时调整边界，或明确 A 暂不满足提前交付条件及后续处理。
边界已明确但代码隔离尚未实现时，可以落实需求材料，并分配隔离设计、实施和验证；不要要求 CUT 先改代码。

## 保留整体验收

拆分时就分配原始整体义务，不等待后继全部完成后再返回来源收口。

| 原义务 | 常见承接方式 |
| --- | --- |
| A 自身可用 | A |
| B 自身可用 | B |
| A+B 完整业务链路 | 覆盖最终闭环的后继，通常为 B |
| A 提前交付时的兼容条件 | A |
| 两者共用的安全约束 | A、B 分别落实本范围 |
| 共享契约建设 | 一个明确建设方，另一方依赖或验证 |

A、B 的局部完成不能替代原来的整体判据。未完成 B 时，原整体目标仍未全部实现；CUT 不维护汇总状态，也不改变这个事实。

## 哪些问题影响应用

先解决后继边界冲突、原始义务无去向、缺少取消依据、会改变归属或用户交付承诺的未决决定。
某个后继内部的设计问题可以保留，写明归属和下一步；不要求全项目所有技术问题先解决。
用户已接受“A 提前交付还需完成隔离设计和验证”时，这些后续问题不必阻止材料拆分。不得将这个接受改写为“A 已可上线”。

## 内容复核

程序只能检查已登记条目的结构与去向，不能证明登记清单覆盖了全部原文。
从原材料反向检查目标、边界、验收、异常、约束和未决问题，确认没有漏登或改变含义。
从每个后继检查是否能说明自身目标、验收、依赖、已有事实与剩余工作。
检查是否存在重复建设、无人承担的整体验收、被隐藏的发布前提或无依据的完成继承。
只报告实际可支持的结论。使用“已登记条目均有去向”“尚有某项发布条件待验证”，不输出无范围限定的 PASS。
