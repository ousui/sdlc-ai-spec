2. 安装

插件正式分发内容在仓库的 dist/。安装插件时不需要构建源码，也不需要安装 Spec Kit CLI；运行已安装插件只依赖 Bash、Python 3.9+ 和常见 POSIX 工具。

3. 初始化项目

插件只需要安装一次，但每个业务项目通常需要执行一次 sdlc-000-init。多根工作区务必指向真正的业务项目根目录，不要误选外层 Git 根。

初始化调用

Codex：$sdlc-000-init
Claude：/sdlc-ai-spec:sdlc-000-init
Cursor：/sdlc-000-init

初始化后主要目录

.sdlc/
├── init-options.json
├── README.md
├── memory/constitution.md
└── specs/

INIT 不会生成需求、方案或任务；第一个需求由 sdlc-100-spec 创建。重复 INIT 是按“保留已有数据、补缺失内容”的思路设计的，不是 reset，也不会自动清空已有文档。

4. Skill 怎么用

000 INIT→010 RULE→100 SPEC→[110 CLAR]→200 PLAN→[210 HUMA]→300 TASK→[310 XCHK]→400 IMPL↔500 CONV

方括号表示按风险选用；HUMA 推荐在 PLAN 后、TASK 前，但不是 TASK 的强制前置步骤。编号不授予自动跨阶段执行权限。

Skill什么时候用你期望得到什么
sdlc-000-init项目第一次接入插件时建立 .sdlc 工作区与项目级基础数据
sdlc-010-rule新项目，或项目规则需要显式更新时项目宪法/规则，后续需求都受它约束
sdlc-100-spec开始一个新需求明确“要做什么、用户价值、边界、验收要求”
sdlc-110-clar需求存在明显歧义、缺口、关键决策不清时通过有限澄清降低规格歧义；简单需求可不必机械执行
sdlc-200-plan规格已足够稳定技术方案、架构、实现路径和工程约束
sdlc-210-humaPLAN 后、TASK 前按需使用；已有任务时也可再次评审需求需求质量评审清单生成；新条目未勾选，评审者判断需求质量，不是功能验收
sdlc-300-task方案确定后可执行的 tasks.md 实施任务清单
sdlc-310-xchk复杂需求、准备实现前只读检查 SPEC / PLAN / TASK 的冲突、重复、遗漏和覆盖缺口
sdlc-400-impl任务已经可执行真正修改业务代码，执行并完成 tasks.md
sdlc-500-conv一轮实现完成后把“实际代码”重新与 SPEC / PLAN / TASK 对照；有差距则追加剩余任务，再回 IMPL
sdlc-status任何时候需要查看当前事实只读展示当前需求、产物路径、任务勾选和诊断，不自动修复或推进流程

推荐使用原则

  • 不要把所有 Skill 当流水线按钮机械全点一遍。 CLAR、XCHK、HUMA 是否需要，取决于需求复杂度和风险。
  • 每个阶段都应把当前业务需求自然语言直接告诉 Agent，不需要人为拼接 shell 参数。
  • 需求级主线一般是：SPEC → PLAN → TASK → IMPL → CONV。
  • 复杂/高风险需求，先用 CLAR 澄清，在 PLAN 后用 HUMA 评审需求质量，在 TASK 后用 XCHK 检查跨文档一致性。

三类检查，不是同一种验收

能力要回答的问题不代表什么
210 HUMA需求是否写清权限、边界、异常行为及可衡量的验收要求？不是功能测试；生成清单不等于评审完成
310 XCHK规格、方案、任务是否矛盾或缺少覆盖？不列出或补齐全部实施操作；它是只读分析
500 CONV代码是否满足既定规格、方案和任务？不是业务验收或发布批准；有缺口只追加任务
谁来打勾：HUMA 新生成或追加的自定义条目必须保持未勾选；评审者明确要求后，AI 才协助评估需求质量。内置 checklists/requirements.md 由 SPEC/CLAR 维护，是独立例外。
400 开始前：IMPL 读取已有清单；存在未勾选项时先询问是否继续并等待回答，不修改清单标记。它不是自动全勾选，也不是无论用户如何回答都禁止实施。

6. 什么场景算“一个需求完成了”

以下都不能单独证明需求完成： spec.md 存在、plan.md 存在、tasks.md 全部打勾、STATUS 显示 ok、Agent 说“已经完成”、代码能编译。

以下是团队可采用的完成标准建议，不是 Spec Kit 新增的阶段或硬门禁。项目是否需要人工验收，应按项目规则与风险决定：

  1. 规格闭合：需求边界、关键行为和验收要求已经明确，没有阻塞性的待澄清项。
  2. 实现与计划一致：代码实现覆盖已确认规格和方案，没有偷偷扩大/缩小范围。
  3. 任务已处理：tasks.md 中本需求应做的任务均已完成；如有取消/替代，需要有清晰原因，而不是简单勾选。
  4. CONV 无剩余差距：执行 sdlc-500-conv 后，不再发现需要追加到 tasks.md 的实现缺口；如果 CONV 新增任务，就回到 IMPL，直到再次收敛。
  5. 工程验证通过：项目自身适用的测试、静态检查、构建、必要的人工验收通过。SDLC Skill 不替代项目真实测试体系。
  6. 没有未解决的阻塞问题：例如安全风险、数据迁移问题、兼容性失败、关键人工验收未完成等。
一句话判定：“该做的已经实现 + 实现和规格一致 + 收敛检查没有新缺口 + 项目自己的验证通过”，这时才可以把需求标记为完成。
验收发现问题后，先分类：
规格明确但代码错误：将证据交给 CONV 对照原意图复核，追加任务后再 IMPL、验证、CONV。
规格有歧义或遗漏：先确认并修订当前需求，按需同步方案/任务，不让 IMPL 猜需求。
新增范围：按需求变更或新需求处理，不让 CONV 悄悄扩展原范围。
实现完成、业务验收完成、发布上线完成应分别说明；收敛不授予 commit/push/合并/发布权限。

7. 查看状态：优先用 sdlc-status

sdlc-status 是只读辅助 Skill，适合回答“我现在做到哪了”“当前需求目录在哪里”“还剩哪些任务”。它不会自动切换需求、不会初始化、不会改任务、不会执行下一阶段。

# 在 Agent 中直接调用：
sdlc-status

# 常见意图：
“查看当前项目和当前需求状态。”
“列出当前项目所有需求。”
“查看 001-login-lock 这个需求还有哪些未完成任务。”
注意：STATUS 的 ok 只表示“可观察事实读取正常”，不表示业务验收通过；任务 100% 勾选也不表示测试、CONV 或发布准备已经通过。

8. 出问题怎么办

现象优先检查处理建议
找不到 Skill / 菜单没有命令插件是否安装到正确用户作用域；是否新开会话/Reload；是否加载了旧 ID sdlc正常卸载旧插件，重新安装 sdlc-ai-spec，确认 dist/skills 能看到 11 个入口。
更新后行为还是旧的实际安装缓存中的 BUILD.json / build_id不要只看仓库 checkout；卸载/重装并重新加载客户端，核对安装副本。
提示项目未初始化当前工作目录是否真的是业务项目根；是否存在正确的 .sdlc明确项目目录后执行 sdlc-000-init。多根工作区不要误选父目录。
INIT 因旧数据/异常目录停止是否存在 .specify、无效 JSON、未知 layout、symlink 或异常文件类型不要删数据硬绕过。先审查异常来源；修复具体状态后再重跑 INIT。
不知道当前需求是哪一个sdlc-status 的 selection / feature 信息先 STATUS，不要靠 Git 分支名或文件修改时间猜当前需求。
HUMA 刚生成清单，400 就询问是否继续自定义清单中的未勾选项这是原版实施前检查。先评审需求质量；或明确决定是否仍继续。不要让 Agent 为通过检查自行打勾。
任务都勾了但感觉没做完是否执行过 CONV；项目测试是否实际通过执行 sdlc-500-conv；若追加任务，回 sdlc-400-impl。
某阶段突然要求额外写文件/跨阶段操作是否超出了该 Skill 原有职责和本次用户授权停止并复核。Skill 被模型自动选择不等于获得额外写入、发布或跨阶段权限。
Claude/Cursor/Codex 三端表现不一致调用格式、插件来源/ref、build_id、客户端版本先确认三端是否实际加载同一个构建，再判断是否是宿主差异。

不要这样修

  • 不要为了“重新初始化”删除整个 .sdlc。
  • 不要把旧版插件目录直接覆盖/合并到新版目录。
  • 不要看到 STATUS partial/error 就让 Agent 自动改文件来“修状态”。
  • 不要跳过业务测试，只凭 Skill 流程结果宣布完成。

9. FAQ

Q：每个需求都必须跑 110 / 210 / 310 吗？
A：不必机械执行。简单、低歧义需求可以走 SPEC → PLAN → TASK → IMPL → CONV；复杂需求、高风险变更或多人协作时，CLAR / HUMA / XCHK 更有价值。
Q：210 HUMA 是否应在 500 后作为人工验收？
A：不是。HUMA 检查需求写作质量，推荐在 PLAN 后、TASK 前。CONV 后的功能测试、独立评审和业务验收使用项目自己的机制；即使后期重跑 HUMA，它仍然检查需求质量。
Q：RULE 每次需求都要执行吗？
A：不用。RULE 是项目级能力，用于建立或显式更新项目原则，不是每个需求的固定前置步骤。
Q：INIT 会不会覆盖项目已有文件？
A：设计目标是保留已有数据并补缺失内容，不是 reset；已有宪法等文件应保留。
Q：CONV 会改业务代码吗？
A：不会直接改代码。它比较实际实现与规格/方案/任务；发现差距时向 tasks.md 追加剩余任务，再交回 IMPL。
Q：STATUS 能不能帮我自动继续下一阶段？
A：不能。STATUS 只读，不调度流程，也不授予新的写权限。

  sdlc-400-impl

  sdlc-500-conv          # 直到没有剩余实现差距
