# 使用流程、评审职责与需求完成标准

本指南面向使用已安装插件的开发者。安装与固定 beta 缓存核验见
[INSTALLATION.md](INSTALLATION.md)，项目初始化见 [INITIALIZATION.md](INITIALIZATION.md)，
离线单页手册见 [quickstart.html](quickstart.html)。

## 1. 推荐路径，不是编号状态机

每个业务项目通常先执行 `sdlc-000-init`，再用 `sdlc-010-rule` 建立项目原则；
已有原则需要变更时显式更新，不必每个需求重跑项目级步骤。

```text
简化路径：100 SPEC → 200 PLAN → 300 TASK → 400 IMPL → 500 CONV

完整路径：100 SPEC → [110 CLAR] → 200 PLAN → [210 HUMA]
          → 300 TASK → [310 XCHK] → 400 IMPL → 500 CONV

实现缺口：500 CONV 追加任务 → 400 IMPL → 再次 500 CONV
实现收敛：进入项目要求的独立评审、运行验证、业务验收或 PR
```

方括号表示按需求复杂度、风险及项目规则选用。编号表达分类与推荐位置，不新增
执行门禁、跨阶段授权或“只能执行一次”的限制。HUMA 推荐在 PLAN 后、TASK 前使用，
但不是 TASK 的强制前置阶段；已有任务时也可以再次使用，检查对象始终是需求质量。
原版前置检查保持不变：HUMA 需要当前需求与 `plan.md`，不要求完整 `tasks.md`；
XCHK 需要完整的规格、方案和任务；CONV 要在 TASK 生成完整任务且 IMPL 对当前任务
执行过之后使用。不要用编号代替实际前置检查。

## 2. HUMA、XCHK、CONV 分别检查什么

| 能力 | 检查对象与问题 | 产物和写入边界 |
| --- | --- | --- |
| `sdlc-210-huma` | 需求是否完整、清晰、一致、可衡量，领域风险与边界是否写明？ | 生成或追加 `checklists/<domain>.md`；新条目保持未勾选，由评审者判断需求质量 |
| `sdlc-310-xchk` | `spec.md`、`plan.md`、`tasks.md` 是否冲突、重复、歧义或缺少覆盖？ | 严格只读报告，不生成实施任务、不自动修正文档 |
| `sdlc-500-conv` | 当前代码是否满足既定规格、方案和任务，有哪些实现缺口？ | 仅向 `tasks.md` 追加收敛任务；无缺口时不改任务文件，不直接改代码 |
| 项目验证与验收 | 实际运行、业务行为、集成、性能等是否满足项目要求？ | 使用项目测试、评审与验收机制；不是 HUMA 的另一种调用方式 |

以“管理员导出报表”为例：HUMA 问“是否写清权限、数据范围和失败行为”；XCHK
检查“规格只许管理员、方案却允许所有用户”的冲突；CONV 发现代码未落实管理员
校验；运行验收则实际验证普通账号被拒绝、管理员得到正确文件。三类 Skill 有
关注点交集，但不能把跨文档一致、需求质量通过和系统运行正确当成同一个结论。

## 3. 如何使用 HUMA

在 PLAN 后按实际风险选择清单主题，例如：

```text
Codex：$sdlc-210-huma
Claude Code：/sdlc-ai-spec:sdlc-210-huma
Cursor：/sdlc-210-huma

为当前需求生成 API 权限与数据一致性的需求质量评审清单。
重点核对规格是否明确权限、并发、失败与恢复、兼容性及可衡量验收标准。
检查需求描述，不生成接口执行步骤或功能测试用例。
```

这类输入交给 Agent，不是 shell 命令。HUMA 可以就实质影响清单内容的缺口提问，
按原规则生成新文件或追加已有清单；生成清单不等于评审完成。

评审者随后逐项对照需求证据。明确要求后，AI 可以协助评估，例如：

```text
请协助评审 checklists/security.md：逐项给出规格/方案依据，
区分已满足、未满足与证据不足。本轮只报告，不修改勾选或业务代码。
```

清单项问“需求是否写明”，不是“产品是否已经实现”。发现需求缺口时先明确范围，
按授权修订当前规格及必要的方案/任务，再继续对应检查；不要为了通过清单而直接
勾选。清单职责取决于检查对象和评审责任，不取决于操作者是人还是 AI。

## 4. 三类复选框与 IMPL 前置检查

| 位置 | 勾选含义 | 谁负责 |
| --- | --- | --- |
| 自定义 `checklists/*.md` | 评审者认为需求质量标准已满足；不是实现完成 | 评审者；明确要求后 Agent 可以协助评估 |
| 内置 `checklists/requirements.md` | 内置规格质量检查项的状态 | SPEC / CLAR 维护，不把此例外扩展到自定义清单 |
| `tasks.md` | 对应实施任务已经完成 | IMPL 完成任务后更新 |

IMPL 在实施前读取已有 `checklists/` 中的清单。如果存在未勾选项，报告状态并
询问是否仍要继续，等待用户回答；全部勾选则按原流程继续。IMPL 不修改清单文件
或标记，不自行把未勾选项变成通过，也不是无论用户如何回答都禁止开发的硬阻断。

## 5. 什么情况下一个需求算完成

IMPL 包含任务实施和适用的完成验证；CONV 对照既定产物检查当前代码，发现缺口
则追加任务并建议回到 IMPL；无可行动缺口则建议进入评审或 PR。CONV 并不授予
commit、push、合并、发布或上线权限，也不能替代真实测试结果。

团队可以采用以下**项目完成标准建议**，不将它变成插件新增阶段或内置硬门禁：
需求边界与验收标准明确，范围内任务确已完成，CONV 未发现剩余实现缺口，适用的
测试/静态检查/构建通过，项目要求的独立评审和业务验收完成，没有阻塞问题。
是否必须人工验收由项目规则和风险决定；不能因为名字含 Human 就强制调用 HUMA。
工程实现完成、业务验收完成、发布上线完成分别说明，不用一个“完成”覆盖未执行项。

后续检查发现问题时分类处理：

| 问题 | 回退方式 |
| --- | --- |
| 规格已明确，代码遗漏或错误 | 将证据交给 CONV 对照原意图复核；追加可追溯任务，再 IMPL、验证、CONV |
| 规格有歧义、遗漏或错误 | 先确认需求并修订当前规格；按需同步方案/任务，再复查一致性，不让 IMPL 猜需求 |
| 提出原范围之外的新能力 | 明确作为需求变更或新需求处理，不让 CONV 自动扩大已确认范围 |

## 6. 常见误区

“310 列完所有操作”不成立：任务由 300 生成，310 只读分析，零发现不等于穷尽
全部问题。“HUMA 清单打勾”不等于代码完成。“CONV 收敛”不等于测试、业务验收或
发布通过。“STATUS ok”只表示文件事实读取正常，详见 [STATUS.md](STATUS.md)。

历史 `sdlc-320-huma` 已由 `sdlc-210-huma` 替代，不是把它改为 510 后置验收。
如仍看到旧入口，检查实际安装缓存的 build_id 并按安装文档更新完整插件；不要
混合两版包或删除项目 `.sdlc`。既有需求文档、自定义模板和清单不自动迁移。
