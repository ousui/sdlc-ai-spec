# SDLC AI SPEC 命名与迁移契约

状态：**用户已确认命名；运行时改名尚未实施**。本文件约束后续转换和上游升级，
不是已完成迁移或客户端验收的声明。流程记录使用
[PR #24](https://github.com/ousui/sdlc-ai-spec/pull/24)，初始工作基线为
`13273b95bbf6db8b7caf5b97011fd9e9a39fa46e`，产品版本保持 `1.0.0-beta`。

## 1. 权威映射与原则

完整 Skill 表在 [README](../README.md#skill-命名与含义已确认的迁移目标)。
[命名映射](naming-map.json) 是同一约定的机器可读表示。修改约定时必须同时更新
这两个文件及本契约，并在 PR 说明原因；不能由升级程序自行推导新名字。

**改名不改行为。** 方法、变量、目录和文案可以变化，但调用方、被调用方、
路径解析、返回字段与模板引用必须在同一迁移中保持对应。不得借命名迁移新增
流程、修改检查责任、放宽写入权限或把未执行的验证写为通过。

| 场景 | 目标名称 | 说明 |
| --- | --- | --- |
| 产品显示名称、文档标题 | SDLC AI SPEC | 使用该大小写 |
| 插件机器标识、包身份 | `sdlc-ai-spec` | 当前仍为 `sdlc`，迁移须同步 namespace 与 marketplace |
| 项目数据目录 | `.sdlc` | 保留，不为品牌统一移动已有项目数据 |
| 环境变量与常量前缀 | `SDLC_` | 大写、下划线 |
| 内部函数等程序简称 | `sdlc` | 遵循对应语言命名风格 |
| 阶段 Skill | `sdlc-<三位编号>-<四字母代号>` | 以命名映射为准，不猜测缩写 |
| 非阶段导航 | `sdlc-status` | 预留名称，当前未实现 |

000–099 表示项目级前置能力，其余已定义编号表示需求级能力。编号不是
状态机，也不表示阶段只能调用一次。`xchk`、`huma` 是本项目代号，不宣称为
行业标准缩写。

## 2. 转换必须按上下文分类

### 2.1 程序标识

已确认的示例映射：

```text
SPECIFY_INIT_DIR          -> SDLC_INIT_DIR
SPECIFY_FEATURE          -> SDLC_FEATURE
SPECIFY_FEATURE_DIRECTORY -> SDLC_FEATURE_DIRECTORY
find_specify_root         -> find_sdlc_root
resolve_specify_init_dir  -> resolve_sdlc_init_dir
```

程序可以执行批量转换，但必须基于明确的标识边界和适用文件分类。实际实施前
先清点完整的声明与引用；示例不是“除此之外都可以忽略”的清单。新上游出现
未识别的运行标识时，升级候选必须报告待审项，而不是猜一个目标名称后继续。

若保留旧环境变量兼容性，必须另行记录别名范围、优先级和冲突处理；新旧值
冲突不能悄悄选一个。不得在普通产品提示中继续推荐旧变量。

### 2.2 能力与宿主调用引用

`specify` 作为上游能力 ID 时映射到 `sdlc-100-spec`，不是 `sdlc-sdlc`。
其余能力严格使用 `naming-map.json`；目录名、SKILL.md 的 name、工作流引用、
提示文本、宿主命令引用与测试期望必须同步。宿主调用前缀和插件 namespace
仍按各自真实契约处理，不因共享名称就假定参数替换或调用策略完全相同。

例如本次目标包括：

```text
sdlc-specify        -> sdlc-100-spec
sdlc-analyze        -> sdlc-310-xchk
sdlc-checklist      -> sdlc-320-huma
sdlc-converge       -> sdlc-500-conv
/sdlc:sdlc-plan     -> /sdlc-ai-spec:sdlc-200-plan
```

最后一项是 Claude 插件调用身份随机器标识一起迁移的示例，不是三个宿主
通用的调用字符串。产品显示名不能直接充当包含空格的机器标识。

### 2.3 产品文案与英文正文

我们交付的入口、生成流程、模板、帮助、错误提示和常规使用文档统一使用
本项目名称。诸如 `Spec Kit project` 的产品性称呼应换成 `SDLC AI SPEC project`。
普通英文动词需按语义改写，例如 `specify the requirements` 可改为
`define the requirements`，不能机械替换成产品名称。

规范性词语（MUST、SHOULD、只读、追加等）、检查对象、责任归属、任务编号
以及输入输出契约不得因此改变。正文改写需要可审查的明确映射，不通过删除
段落、任意空白归一化或宽泛忽略规则来让独立比较通过。

### 2.4 路径与正式产物

`.sdlc` 已是本产品简称，继续保留。`spec.md`、`plan.md`、`tasks.md`、
`memory/constitution.md`、`checklists/requirements.md` 等是既有产物路径契约，
不属于旧产品品牌，不因 Skill 名变化而自动改名。产出物名称或正文中包含的
旧产品/能力标记则必须同步转换。

未来确需为正式产物增加编号或更改路径，应先给出完整路径映射，并一并更新
解析器、模板、覆盖模板和引用；不能只改标题或生成文件。CLAR 更新已有规格，
XCHK 是只读分析，CONV 追加已有任务，不为凑齐阶段文件而改变这些行为。

## 3. 保留真实来源，但不把来源 ID 当作产品入口

以下资料中的上游名称具有来源意义，不执行产品化替换：

- `src/upstream/`：保持与锁定上游逐字节一致，包括原始命令名和源码路径。
- `upstream.lock.json`：保留真实仓库、提交、文件路径和哈希，不伪造来源。
- `LICENSE`、`NOTICE`、生成包的 `UPSTREAM.json`：保留版权、许可与真实引用。
- 独立基线验证中确实调用的上游 CLI、来源差异账本和明确的旧数据检测案例：
  必须标明这是上游验证或兼容性资料，不是本产品使用方式。

`source_id: specify` 等映射值是上游来源 ID，不是生成后的公开 Skill 名。
上游源码可以不动来降低升级成本，但这不允许构建出的产品继续泄漏旧调用
名称、未替换占位符或让用户误用上游命令。不要以“上游原文不能改”为理由，
把应转换的生成文案保留下来；应在生成层显式转换。

例外必须按文件、字段或用途可解释地列出，不能笼统把整个 dist 排除出检查。
已有版权不因产品作者为 Blade 而被删除。实际 Git author/committer 与产品作者
分开记录，不把元数据更新描述成仓库转移或提交身份修复。

## 4. 升级迁移流程

后续维护 `tools/port.py`、`tools/render.py`、`tools/build.py`、`tools/upgrade.py`
及独立验证时，必须先读取本文件。适用原则也应在修改的转换函数附近注明，
引用本契约，避免未来仅照搬上游生成器把旧名字重新带回来。

1. 在独立候选中读取锁定的上游原文；保留原始来源资料，禁止覆盖已接受目录。
2. 使用确定性、按上下文分类的映射生成自己的源码投影和安装包；不在安装时
   临时改名，也不手工修改已经生成的 wrappers、bindings 或 workflows。
3. 同步全部引用、三个宿主清单、根 marketplace、程序变量、用户提示和文档。
   生成层与运行层职责不混淆；迁移不能改变包根/项目根隔离及路径安全规则。
4. 独立核对上游实际输出与转换后的行为；名称映射是有限、可审查的差异，
   不是跳过正文比较、脚本差分测试或失败对照的理由。
5. 重复生成必须字节确定；输出中残留的旧产品标记、悬空引用和未知命令必须
   报告。检查整个调用链，而不只搜索 README 或 SKILL.md 文件名。
6. 验证后把准确 source SHA、生成树/包摘要、命令、结果和未执行项追加到 PR；
   只有对应版本的证据可用于接受，不能引用旧 PASS 代替本轮回归。

## 5. 行为不变与后续独立工作

INIT 保留现有幂等补全行为，不覆盖已有数据。RULE 保留项目规则维护职责；
XCHK 严格只读；HUMA 生成评审者拥有的需求质量清单；CONV 仅追加差距任务，
不直接实现代码，无发现时不产生空的收敛章节。

以下是已讨论但不由本次改名自动实现的能力：RULE 代初始化、`sdlc-status`
实际状态展示、`dist/skills` 公共入口与宿主策略合并、旧项目数据自动迁移。
不能把预留名称写成已经安装，也不能把命名测试通过写成行为兼容性通过。

## 6. PR 作为工作包流程记录

PR 正文维护目标、批准定义、范围、最新实现/验证状态及未完成项。关键决策、
提交、失败与修正以追加评论保留历史；不通过反复覆盖同一条进度评论隐藏失败。
README 和本契约保存长期规范，不另建一套与 PR 重复的流水进度平台。

每次代码更新至少记录：准确提交 SHA、本次变化、实际验证命令与结果、
未验证边界。对外报告先核实远端分支与 PR 的 HEAD。Draft、CI 通过、原生宿主
验证、业务验收和可合并是不同状态，不互相替代。不得自行合并、改标签、发布
或改写其他分支历史。
