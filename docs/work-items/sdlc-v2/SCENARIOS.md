# 三项目、三轮场景与验证边界

> **速读：基础轮沿用实验室原要求；复杂轮每项目提出一个新需求，共九条真实业务链路。客户端按本地代码核实后固定验收。此文件是执行设计，所有 v2 结果目前均未运行。**

每个场景均实际执行 REQ → DSN → PLN → IMP → VFY → RLS，保留同一需求身份和准确证据。

## 2. R0：原要求基础闭环

> **速读：三个项目必须先全部闭环并本地提交，再启动新需求。由 Agent 在 IMP 生成实现，不把旧 candidate 复制进去后补流程。**

### R0-ADMIN：账户状态与旧库升级

从原轻量 Admin 基线实现用户启用/禁用、后台筛选和修改、已登录会话即时撤销、旧 SQLite 数据库的幂等增量迁移。保留实验室原安全准备（环境变量配置、非破坏性空表初始化）及许可证；不声称这是生产完整 RBAC。

冻结测试：既有13项行为断言；登录、禁用后既有会话、再次启用需重新登录、过滤一致性、旧库重复迁移。VFY 对本轮准确产品对象重新执行；交付到本地 Sandbox 并回读。

### R0-SPRINGGEAR：四模块 JDK21 迁移

保持原四模块和公开 Java 行为，按原设计进行必要构建/兼容性调整，运行 JDK21 的 Maven reactor 验证、10项真实JUnit和class major65检查。禁用的历史扩展模块不计入通过，不迁移Spring7，不推送产品上游，不发布Maven远端包。

建议调用形式按本地记录解析：`mvn -B -ntp verify`，缓存齐备后可用 `-o`。第一次准备依赖的构建不算正式 IMP/VFY 结果。

### R0-FANSITE：本地粉丝站

实现非官方主题主页、粉丝账户、资料隔离、试听、相册和简单后台；媒体使用自产测试音和色块图，使用合成账户。Go依赖离线vendor，不引入npm服务。

测试覆盖原24项真实HTTP/文件行为，加上已约定的JS语法、页面结构检查。参考命令：`GOPROXY=off GOTOOLCHAIN=local go test -count=1 -v ./...`、`go build`、`node --check web/app.js`，具体目录以本地项目为准；有测试失败必须看真实输出。

## 3. R1：跨模块与条件衔接

> **速读：在 R0 产品终态基础上叠加有依赖、异常分支和回归义务的需求，检查模型能否自然把关系写入新内核。**

### R1-ADMIN：批量状态更新、筛选分页与会话一致性

目标：批量启停用户，结果与列表过滤/分页统计一致，禁用立即撤销现有会话；本地隔离数据支持重复请求与部分无效输入。

锁定验收：普通请求与非法ID、混合有效/无效ID的原子策略；当前操作账户保护策略；页面总数与筛选结果一致；重复提交无额外变更；重新启用后旧会话不能恢复。当前示例没有生产角色体系时，不把历史简化权限假装成已有企业权限，所需边界在本轮REQ显式定义。

流程压力点：数据库变更/后端行为/页面过滤多个任务；接口检查是真实执行条件，原型及代码是来源；共享工作区切分支后不能切到另一个需求。

### R1-SPRINGGEAR：可选流水线观察与异常语义

目标：在四模块与现有公开行为内增加可选节点执行观察能力，记录节点开始/成功/失败；默认不开启时保留现有行为。

锁定验收：节点执行顺序稳定；原始异常cause保留；失败后后续节点按明确策略处理；观察器失败不会偷偷改变主业务异常；不同执行实例信息隔离；旧10项测试仍通过。基于现有扩展点实现，若已有等价能力，改为一个同等复杂度的未覆盖能力并先更新需求，而不是重复实现。

流程压力点：设计阶段API兼容边界→实现→集成验证；SpringGear是框架库，不为此新增Web服务或分布式调度器。

### R1-FANSITE：发布态搜索、稳定分页和媒体可见性

目标：对音乐/相册增加筛选、搜索、稳定排序和分页；草稿、下架、删除内容的列表/详情/媒体URL访问一致。

锁定验收：正常/边界分页、同排序键稳定、过滤后的total、未授权访问、下架后旧媒体URL不可用、重启后状态一致。既有登录/CSRF/媒体24项断言继续通过。

流程压力点：数据层、HTTP、原生JS的多任务和验收覆盖；本地已有数据的增量变化，而非全新应用重新生成。

## 4. R2：变更、并发与恢复

> **速读：承接 R1 的结果，再加入会暴露状态和证据绑定问题的需求。故障注入与正常路径分轨保存。**

### R2-ADMIN：状态变更审计与请求幂等

目标：为R1状态修改增加可查询审计记录和幂等操作键；重复请求不重复修改或追加同一动作，错误不能留下半成品状态。

锁定验收：审计记录能追踪操作者/目标/前后状态；同键同请求幂等、同键异请求冲突；迁移重复执行无破坏；写入失败状态与审计原子一致；旧会话撤销保持；过滤/分页与原13项回归通过。凭据/会话原值不入审计。

专项：复制到worktree实施，主库同时有另一需求；交回保留双方。相同需求双侧修改时显示冲突而非覆盖。

### R2-SPRINGGEAR：并行执行上下文隔离与资源清理

目标：在现有JDK21框架内保证并行运行的工作流上下文隔离，异常结束后清理执行态，不影响原有串行语义。

锁定验收：用可重复的同步屏障而非sleep猜测验证并发；两条执行不串上下文/观察事件；异常后重试/重复调用按明确规则工作；原cause保持；原四模块、旧行为与R1观察器检查全部通过。必要变更限制在本轮需求，不顺手重构所有扩展。

专项：合入一个与当前任务无关的基线提交可继续；涉及公共执行组件变化时必要复验，不复用旧对象的PASS。

### R2-FANSITE：并发编辑冲突与落盘失败一致性

目标：内容编辑使用明确版本约束，过时更新能识别冲突；持久化失败不能对外暴露半成功内存状态或悬空媒体引用。

锁定验收：两个编辑器读同版本，首个更新成功、第二个返回明确冲突；重读后可正确更新；磁盘失败注入保留旧可读状态；重启后一致；删除/下架不残留可访问媒体；旧24项及R1新增测试继续通过。

专项：执行中断保留Run，移机读取`.sdlc`能定位最近任务、错误和已保存附件；恢复前识别未完成副作用，不盲目重放。

## 5. 固定证据口径

> **速读：验收目标先于实现固定；成功路径和故障注入分开，真实 Agent 执行与脚本回归分开。**

每个场景开始前保存一页需求及验收。测试可在IMP中实现，但不得因为失败删减原断言；发现需求确有冲突时在来源和变更记录中说明。新轮次需求允许结合本地代码进行等价细化，不能把复杂场景降成只改文档或增加一个无关小函数。

最终九场景矩阵列出：需求ID、Runtime SHA、实验室SHA、产品输入/输出对象、实际宿主与模型、六Skill是否真实运行、业务测试结果、终态收敛/交付、人工修补次数、非预期阻塞/异常、原始证据路径。

“应用测试通过”不自动证明“六Skill可用”；“执行了六个CLI”不自动证明“Agent没有预制全部阶段答案”；“旧candidate业务通过”不证明本轮完成实施。三层证据都要可追溯。
