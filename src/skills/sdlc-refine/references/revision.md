# 内容修订标准

本标准用于已有 SDLC 资料的整理、校正、补全和重梳。根据本次目标使用相关规则，不把每个小改动扩展为全项目审计。
“不规范”必须能对应明确约定、错误或使用障碍；新模板与旧文档长得不同，不自动构成错误。

## 依据与冲突

- 以当前用户指令、明确获准的业务决定、项目宪法及适用约定确定修订目标。历史决定冲突时说明各自适用范围与来源；不按文件时间推定谁已取代谁。
- 原始需求与已确认补充提供业务依据，现有 spec/plan/tasks 提供当前表达。代码和测试用于观察实现与验证事实，不能默默反向改写需求来迁就实现。
- 引用保留文件、条目或决定来源。行号只适用于实际读取的版本；需要重排时补充稳定编号或去向映射。
- 缺少来源只能提出建议或待确认项。用户已给出明确取舍时落实决定，不重复要求批准同一事项。

## 常见问题的处理

| 问题 | 可以落实的修订 | 仍需明确的事项 |
| --- | --- | --- |
| 表达、术语、标题或格式混乱 | 按已选约定统一表达、分清层级，保留实际 API、代码标识和机器 token | 有业务差异的近义词不能直接替换 |
| 路径、链接、编号或引用错误 | 核实真实目标并修复引用，必要时同步关联材料 | 多个候选目标、重复 ID 的引用归属需要依据 |
| spec、plan、tasks 相互矛盾 | 按明确需求或决定修正偏离的表述与必要关联 | 原始业务要求本身冲突时列出待决项 |
| 相关内容遗漏 | 将已有明确要求或决定补到应在的位置，保留来源 | 没有事实依据时不能补造需求或设计 |
| 重复、分散或结构混乱 | 合并语义确实相同的叙述、重组章节、梳理依赖与导航 | 表述相似但约束、责任或场景不同的内容应保留区别 |
| 完成声明、勾选或评审结论可疑 | 区分现有声明与证据，记录疑点；落实用户已明确给出的更正决定与依据 | 不自行判定阶段完成，不因存在代码或旧测试通过而批量改状态 |
| 历史版本或模板不一致 | 兼容读取已有格式；明确要求规范格式时按目标呈现整理 | 插件版本适配另按兼容标准，不自动刷新初始化历史或 provenance |

稳定 ID 尽量保留。确需修复重复或失效标识时，建立旧→新映射并检查受影响引用；归属有歧义时不能猜配。
机器标记、参数、schema key、任务复选框和追踪语法保持实际契约。不能以“规范化”为名擅自更改它们的业务含义。
用户已明确要求统一文档呈现时可整理既有标题与格式；没有此要求时沿用能正常使用的风格，旧英文、双语和中文形式均可读取。

## 重梳时保留什么

逐项核对本次受影响的目标、用户/故事、功能、非功能约束、验收、依赖、排除项、任务、未决问题及历史证据。
每项在新结构中有去向，或有用户明确决定的移除依据；内容更短不代表覆盖更完整。

- 整合重复文字时保留例外条件、适用范围和来源，不因标题相同就合并义务。
- 调整任务叙述、顺序或分组时保留原任务责任、依赖和完成依据。拆并任务会影响已完成部分时先形成对应关系，不能直接继承整个任务的勾选。
- 把事实、建议和待决事项分开；原来的未知与风险不能被流畅文案掩盖。
- 宪法原则及业务承诺的改变需要明确决定；普通文档整理不隐含取消需求、降低验收标准或绕过人工评审。
- 历史测试记录、验收证据和生成 provenance 保留其来源及适用基线，不把过时证据改写成当前通过。

## 复核与交付

从旧材料反向检查新内容，确认义务和未决项没有遗失；从新内容反向检查依据，确认没有凭空新增事实。
检查跨文件术语、编号、引用和依赖，再核对用户明确要求的呈现约定。结果说明修正了什么、依据是什么、哪些仍待决定或核验。
资料整理不代签 HUMA 评审、不代替 XCHK 只读分析或 CONV 实现检查；若用户已提供这些检查结果，可据其证据在本次明确修订范围内处理。
