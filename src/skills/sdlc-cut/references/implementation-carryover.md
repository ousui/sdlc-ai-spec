# 材料与实现承接

## 基本原则

分别处理业务代码、需求材料和完成事实。代码保留原位置；材料按后继范围重组；完成与验证结论针对后继实际使用的基线判断适用性。
需求目录不是代码目录或分支。创建两个后继需求不会复制两套源码，也不自动创建两条开发分支。
CUT 不移动代码，不拆提交，不 stash、reset、cherry-pick、rebase、提交、推送、合并或部署。

## 材料迁移矩阵

| 原材料 | 承接方式 | 应避免的失真 |
| --- | --- | --- |
| spec | 按目标、故事、要求、验收和边界重组，保留来源 | 完整复制父规格后只换标题 |
| plan | 保留适用约束、设计与决策，明确因新边界产生的缺口 | 原 A+B 方案原样复制后宣称全部适用 |
| tasks | 调整归属与依赖，保留完整来源映射 | 全部勾选、全部清零、重复实施 |
| contracts、data-model | 提取后继适用内容，共享协议明确来源与责任 | 两份冲突协议同时作为权威 |
| research | 保留结论、前提、拒绝理由和依据 | 脱离适用条件继承历史决策 |
| quickstart | 保留适用场景，明确中间交付需要验证的内容 | 完整 A+B 环境结果冒充 A 单独可发布 |
| checklists | 保留条目、来源与适用原评审依据 | 删除未完成项或由 CUT 补造人工批准 |
| 历史验证报告 | 保留原报告并说明适用范围 | 批量复制 PASS、CONV 结论 |
| 其他附件 | 清点后说明迁移、引用或历史留存 | 未识别即丢弃 |
| 项目公共约束 | 读取并引用 | 在拆分中改写项目规则 |

关键约束、共享基线、兄弟需求共存边界和发布限制应出现在后继适用的标准文件中。
同一个共享建设任务明确一个责任方；各后继仍承担本范围的集成验证。共同安全、性能等约束可同时适用多个后继。

## 任务完成事实

| 来源与实际观察 | 后继处理 |
| --- | --- |
| 已勾选，实现在后继将使用的基线，范围和完成依据仍成立 | 可继承完成标记，登记来源任务、实现和依据 |
| 已勾选，但范围变化或原依据不适用 | 保留历史完成声明；后继复核相关条件，不无条件继承通过 |
| 未勾选，已实现一部分 | 剩余工作仍未完成，说明已有实现和待补内容 |
| 未勾选，尚无实现 | 承接未完成任务 |
| 未勾选，但观察到完整代码形状 | 记录观察，不仅凭文件存在自动勾选 |
| 原任务覆盖 A/B 多项义务 | 拆出实际义务，或明确共享建设责任与引用 |
| 代码只在其他分支，后继基线不包含 | 不继承为后继已完成；记录引入或核验基线的后续工作 |

任务使用原版复选框语法。部分实现、待核验是普通说明，不引入新状态。
已存在工作无需因为拆分重做；把后继未完成任务写成“核验既有实现并补齐剩余条件”，不能让读者误以为全部从零开始。
可以在各后继中使用各自正常的 T001、T002，但映射须限定来源，例如 002/T014 → 004/T006。
承接原任务的一部分时，写清被保留、分出和剩余的具体义务，不能只按相似标题映射。

## 基线与未提交改动

允许在有未提交改动的工作区分析与拆分。不要要求自动提交，也不要清理用户工作区。
Git 可用时，将本次承接判断依赖的每个相关文件传给 `inspect --observe-code`；只读记录 HEAD、可取得的分支、相关 HEAD→暂存区与暂存区→工作区变化、有关未跟踪文件及其当前字节摘要。即使工作区字节与 HEAD 相同，也要检查暂存区是否另有内容；避免只读查询隐式更新 Git 元数据。
记录与本次承接有关的文件，不复制整个代码仓库作为 CUT 状态。
当前工作区独有的实现只能说明“在当前工作区观察到”。后继转到其他分支或工作树时必须重新核对是否存在。
摘要用于发现变化，不是代码备份。没有 Git 时使用文件观察和明确限制，不编造 commit。
应用前对照相关观察；变化使承接依据失效时，更新分析和方案，不套用旧结论。

## A/B 实现混合且 A 先交付

检查共享数据迁移、启动路径、后台任务、接口和权限，以及 B 的未完成部分是否可能随 A 暴露。
不要仅凭页面被隐藏判断后端或运行行为已隔离；不要根据文件名或提交标题机械拆代码。
给适当后继明确分配以下工作：

1. 确认实际部署基线与发布包中的 B 改动。
2. 确认共享接口、数据迁移和运行前置。
3. 在正常规划中确定隔离方式。
4. 在正常实施中落实该方案。
5. 验证 B 未完成或未启用时，A 的行为与验收仍成立。

功能开关、独立发布基线和耦合调整可以成为后续规划候选；CUT 不擅自选择一种。
方案未知时，先登记规划缺口，不生成假装技术方案已确定的具体实现任务。
需求边界已确认、用户接受交付前提且隔离工作有归属时，可以发布拆分材料；独立发布仍待验证这一事实必须保留。

可采用的交接表述：

> 需求材料已经拆分。当前代码包含 A/B 混合改动，A 独立发布条件尚未验证。交付基线、隔离方案及验证由 A 的后续原流程处理。

## 历史清单与验证

保留适用清单，包括未勾选条目，不通过删清单规避原流程条件。
已有勾选只在原评审条件、范围和依据仍适用时连同来源继承。拆分后新产生或改变的人工评审结论由原责任方处理，CUT 不补造批准。
历史报告保持原始结论和适用范围。不要将父级完整环境下的测试结果描述为新的 A 单独交付已经通过。
无法确认适用性的结果写明待核验；不要假装缺少证据等于已经失败，也不能当成已通过。

## 选择继续入口

| 后继实际情况 | 建议 |
| --- | --- |
| 业务范围仍有影响实现的疑问 | 先澄清 |
| 新边界改变方案或发布策略 | 先修订相关规划，并同步任务 |
| 材料完整，需要检查引用、覆盖和依赖 | 按需要使用原 XCHK |
| 方案明确、任务完整一致，剩余工作可实施 | 原 IMPL |
| 当前代码对新规格的覆盖不明，材料齐备 | 按需要原 CONV，再按结果继续 |
| 已具备项目要求的结果 | 按既有评审、验收和发布流程处理 |

这些是交接建议，不替原版作出阶段通过判断。先阅读 [原版兼容规则](sdlc-compatibility.md) 的前置和生成行为。
不机械重跑 SPEC/TASK，不承诺生成器保留迁移后的材料。CONV 不负责迁移，也不是每次 CUT 的必经步骤。
兄弟需求的代码共存应解释清楚，但不能以“属于兄弟需求”为理由豁免其对本需求行为的实际影响。
