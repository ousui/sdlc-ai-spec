# v1.1 Spec Delta Plan

## 1. 工作包状态与边界

本文件只定义从 `docs/v1.0/` 到 `docs/v1.1/` 的精确 Spec 变更计划。它不是正式 Spec，不进入任何 Artifact 的 `Evaluation Contract Set`，也不授权创建 `docs/v1.1/`、实现 Provider、Resolver、Projection 或 Skill。

当前状态：Delta Plan 已完成，等待独立、只读架构审查。审查通过前不得创建 `docs/v1.1/`。

权威输入：

- `docs/architecture/artifact-store-and-projection.md`：已接受的 Store、Projection、Runtime Workspace 与 Retention 架构输入；
- `docs/v1.0/core-spec.md` 与 `docs/v1.0/000-ctx-spec.md`：Artifact、Reference、Gate 与 CTX 语义；
- `docs/v1.0/100-req-spec.md` 至 `docs/v1.0/600-rls-spec.md`：全部 Phase Contract；
- `docs/v1.0/200-dsn-domains/*.md`：全部 16 份 Domain Contract；
- `docs/v1.0/README.md` 与 `SHA256SUMS`：Snapshot 索引和冻结摘要规则。

本计划的唯一目标是解除领域 Contract 与固定物理存储布局的耦合，同时保持 Artifact 内容、Lifecycle 业务语义、字段、枚举、Reference、Status、Gate、Final Confirmation、Evidence、Exception 和责任边界不变。

## 3. v1.0 / v1.1 版本边界

### 3.1 Snapshot 边界

- `docs/v1.0/` 保持字节不可变，创建 v1.1 前后都必须通过现有 `SHA256SUMS`；
- v1.1 是新的完整 Spec Snapshot，不是对 v1.0 文件的原地补丁；
- v1.1 每份正式 Spec 的 Front Matter `version` 使用 `"1.1"`。仅发生该版本元数据、Snapshot 路径或链接变化而无规则变化的文件归类为 `reference-update-only`；
- v1.0 Frozen Artifact 永远由其原 `Evaluation Contract Set` 解释；v1.1 不用新规则重解释旧 Snapshot；
- v1.1 Artifact 可以把兼容的 v1.0 Frozen Artifact 作为 Input，但必须逐条解析其原 Contract Set、Authority、State、摘要和传递 Input 链。

### 3.2 保留的领域语义

v1.1 必须原样保留：

- Artifact ID、CTX ID、Revision 及项目范围唯一性；
- `open / frozen / abandoned` Revision State；
- `draft / waiting_input / failed / ready / ready_with_exception` Status；
- Context、Artifact、Item、Member、Spec、Authority 与 VCS Reference 的现有用途和语法；
- Evidence、Supporting Artifact、Exception、Open Item、Disposition、Check、Gate、Final Confirmation 与全部 Phase / Domain 业务字段；
- 不允许 `latest/current`、目录扫描、内容相似度或查询排序替代准确 Reference；
- Frozen Revision 不可原地修改；
- Pre-execution Checklist 必须在正式 action 前持久化、读回并形成 Evidence；
- 完整 Markdown/YAML Canonical Blob、原生 Supporting Members 与现有 SHA-256 语义。

### 3.3 仅解除的存储耦合

v1.1 只把以下物理概念改写为逻辑 Store 概念：

- 固定 `artifacts/<order>/` 根目录 → 当前 Workspace 的唯一 Canonical Store Binding；
- `revision-index.md` → Store 管理的逻辑 Revision Control Record；
- `revisions/<NNNNNN>/` → 由准确 ID / Revision 标识的 Revision Package；
- `<Artifact-ID>.md` 主文件 → 原始字节可读回的 Canonical Markdown/YAML Blob；
- Supporting Artifact 本地路径 → 稳定 Member ID、Canonical Member Name 或不可变外部 Reference；
- 文件写入与存在检查 → Provider 的原子提交、read-after-write 和摘要读回；
- 目录状态变更 → Store 的 `Freeze` / `Abandon` 原子状态转换；
- 固定目录解析 → Binding-aware Exact Reference Resolve。

### 3.4 Contract 标识决定

| Contract | v1.1 决定 | 兼容依据 |
|---|---|---|
| `sdlc-ai-spec/artifact/v1` | 继续使用 | Lifecycle Front Matter 字段、Artifact ID、Revision、Status、Context、Inputs、正文模板、Reference 与 Gate 均不变；Store Binding 不进入 Artifact |
| `sdlc-ai-spec/project-context/v1` | 继续使用 | CTX Front Matter、Identity、Basis、Item、Status 与 Gate 均不变；只把持久化和解析交给 Store |
| `sdlc-ai-spec/final-confirmation-authority/v1` | 继续使用 | Authority 文件字段、确认绑定和摘要语义不变；项目相对 `Authority Reference` 仍是独立的不可变外部权威引用，不是 Artifact Identity |

同一 Contract ID 跨 v1.0 / v1.1 兼容的前提是字段、枚举、Reference 结构和 Artifact 内容语义不变。Snapshot 差异由准确 `Evaluation Contract Set` 表达，不通过提升 Artifact Contract ID 表达。

### 3.5 Breaking Change 候选与停止条件

当前计划不采纳任何 Breaking Change。后续编制若发现必须执行以下任一项，必须停止 v1.1，登记为 v2.0 或独立兼容性决定：

- 在 Lifecycle 或 CTX Front Matter 新增 `workspace-id`、Store、Provider、Binding 或 Locator 字段；
- 改变现有 Context / Artifact / Item / Member / Spec / Authority / VCS Reference 的语法或字段类型；
- 把 `Artifact Locator` 写入当前只接受领域 Reference 的字段；
- 改变 Artifact、CTX 或 Final Confirmation Authority 的固定字段、章节、枚举、Status、Gate、Final Confirmation 或责任边界；
- 用关系型行、JSON Projection 或 Provider Schema 取代 Markdown/YAML Canonical Blob；
- 改变 Supporting Artifact Manifest 字段结构，而不是澄清 `Path or Reference` 为逻辑 Member Name 或不可变外部 Reference；
- 需要两个 Store 同时对同一 Workspace / Project Boundary Namespace 声明 Authority。

## 5. 新增 Spec 的职责

### 5.1 `artifact-store-spec.md`

决定：新增，属于正式 Spec。

它进入所有 v1.1 CTX 与 Lifecycle Artifact 的 `Evaluation Contract Set`，顺序位于 Core 之后、Project Context / Phase 之前。原因是 Artifact ID / Revision 的持久化、准确解析、冻结不可变和完整性是所有 Canonical Artifact 的通用合规前提。

Normative 内容限定为：

- Workspace Authority Namespace 与唯一 active Canonical Store Binding；
- Store Binding 的最小非秘密元数据及其不进入 Canonical Artifact 的边界；
- `Artifact Allocate`、`Revision Allocate`、`Read`、`Write`、`Freeze`、`Abandon`、`Exact Resolve`、`Query`、`Export`、`Import`、`Promote`、`Integrity Digest` 的可观察语义；
- Revision Control Record、Canonical Blob、Supporting Members 与 Revision Package Digest；
- 原子性或等价事务、条件写入、read-after-write、冲突、崩溃恢复和 no silent fallback；
- Workspace 内短 Reference、跨 Store Locator、跨 Snapshot 兼容与递归 Input Resolve；
- 三档 Retention、Reference 生命周期、删除边界与 Promote 义务；
- v1.0 filesystem Artifact 的只读挂载、Import 与 Promote 兼容规则。

不得进入该正式 Spec 的实现细节：

- SQLite 表、列、索引、PRAGMA、WAL 或文件名；
- `.sdlc/`、数据库文件、lock / journal 的固定路径；
- MCP Tool、REST / GraphQL API、RPC、CLI、请求 Payload 或认证协议；
- OS 文件锁、具体 lease service、Git ref 名称、对象 Key、HTTP 状态码；
- Provider 安装、初始化、备份、运维和故障排查步骤。

这些内容只能进入后续独立的 Provider Profile 或 Guide，且不得成为 Artifact `Evaluation Contract Set` 的一部分。

### 5.2 `artifact-projection-spec.md`

决定：新增，属于正式 Spec，但默认不进入 Canonical Artifact 的 `Evaluation Contract Set`。

它只约束 Projection 的生成、校验、过期判断和 Round-trip。生成 Projection 时，其独立的 Projection conformance 记录必须绑定该 Spec；Canonical Artifact 是否合规仍只由 Canonical Artifact 的 Contract Set 决定。

Normative 内容限定为：

- `downstream`、`human-review`、`export` 三类 Projection；
- Source Locator、准确 Source Reference、Source Revision Package Digest、生成时间、格式版本与 view digest；
- Canonical stable ID 到 View element 的 hidden mapping、mapping digest 与唯一映射要求；
- `stale` / `superseded` 判断和 Source 不可解析时的行为；
- 显式 Round-trip Import、Change Set、条件写入、冲突与 no-op；
- 编辑、保存、接受修订或完成 Review 不等于 Approval；
- Frozen Source 的编辑只能产生新最大 `open` Revision；
- Projection 不提供 Gate、Final Confirmation、Context / Input 或下游 Authority；
- `live-reference`、`self-contained-archive`、`presentation` Retention Mode。

不得进入该正式 Spec 的实现细节：

- Google Docs、Office、HTML、UI、sidecar 或自定义属性的具体字段布局；
- hidden mapping 的 JSON Schema、数据库表或文件名；
- 编辑器插件、MCP/API、Webhook 或同步协议；
- 导出模板、样式、页面布局和平台权限配置。

## 6. Core Spec 精确变化

| v1.0 物理概念 | v1.1 逻辑表达 | 必须保留的不变量 |
|---|---|---|
| 固定 Artifact 根目录与 Phase 目录 | Resolver 从当前 `workspace-id` 的唯一 Canonical Store Binding 解析 Workspace Authority Namespace；Lifecycle 表只保留 Order / Phase / Code | Artifact ID 不能从 Store、路径或表推断 |
| `revision-index.md` | Store-owned Revision Control Record，至少表达 Revision、State、Base Revision、Allocated At、Frozen At、Abandon Reason | Revision 单调递增、不跳回、不删除、不复用；同时最多一个 `open` |
| 六位 Revision 目录 | 准确 `<Artifact-ID>@<Revision>` 对应的 Revision Package；六位目录只属于 filesystem Profile 的排序投影 | Reference 中 Revision 仍是不补零正整数 |
| `<Artifact-ID>.md` 主文件 | 原始字节可读回的 Canonical Markdown/YAML Blob | Front Matter、固定章节、字段顺序、Control Input Digest 不变 |
| Artifact Set 子文件路径 | Stable Member ID + Canonical Member Name；外部内容使用不可变 Reference | Member Reference 和原始字节 SHA-256 不变 |
| 创建文件后报告分配成功 | Store 在 Revision Control Record 与 Canonical Blob 骨架均原子提交并读回后才报告成功 | 分配失败不得复用编号或报告成功 |
| 文件原地修改 | 只允许对准确 `open` Revision 进行 expected digest / Authority Generation 条件写入 | Frozen / Abandoned 不可写，冲突显式失败 |
| 更新 Index 行为 `frozen` / `abandoned` | Store `Freeze` / `Abandon` 原子且幂等地改变准确 Revision State | 合法变化仍只有 `open → frozen / abandoned` |
| 按前缀找目录、Index 行、Revision 目录 | Resolve Binding → Exact Resolve Revision Control Record → 读回 Canonical Blob / Members / digest → 按原 Contract Set 验证 | 任一失败即失败，不查最新、其他 Store、cache 或 Export |
| 通过目录递归解析 Inputs | 每条直接与传递 Input 都按其准确 Reference、Authority、Contract Set 和 Package Digest 递归解析 | 不用下游当前 Spec 重解释上游 |
| 目录内容构成 Snapshot | `frozen` Control Record + Canonical Blob + 完整 Supporting Member 集 + Manifest / Package Digest + Gate / Final Confirmation | Snapshot 完整性、不可变性和下游可解析性不变 |

Core 的以下现有路径型 Reference 不属于 Artifact Store 耦合，必须保留：

- `Spec Reference` 的仓库相对路径与 SHA-256；
- `Authority Reference` 的项目相对路径与 SHA-256；
- `VCS Locator` 的不可变产品内容定位；
- PLN `path:<resource-id>/<resource-relative-path>` 的产品 Execution Scope。

这些 Reference 的解析根必须来自 Artifact 已绑定的不可变 Spec Snapshot 或 Project Resource，不能来自执行主机偶然路径。

## 7. Phase 与 Domain Spec 变化

### 7.1 Phase

- REQ：无 Artifact 物理定位规则；只做 Snapshot version 更新。
- DSN：把“主设计总纲 + Domain 子文件”的物理目录树改为一个逻辑 Revision Package。父 Canonical Blob 仍是唯一总览和 Gate；`DOM-*` 与 `SUP-*` 仍是 Member ID；`domains/<fixed-name>.md` 与 `assets/...` 可作为稳定 Canonical Member Name，并由 filesystem Export 还原，但不能用于发现 Store Authority。
- PLN：`path` Scope Token 只定位被实施产品的版本化 Resource，原样保留；只做 Snapshot version 更新。
- IMP：Claim Resolver 与 Claim Provider 不并入 Artifact Store。Claim `acquire` 成功后的文件物化改为 Store Revision Allocate / Readback；失败恢复改为 Store Abandon。Claim State、Attempt、Owner、Resource 冲突、Rework、Dependency、Gate 后 `Freeze → Claim complete` 顺序不变。
- VFY：Pre-execution 持久化与读回是必须保留的可观察语义；Supporting Evidence 可为 Store Member 或不可变外部 Reference，不要求本地文件；只做 Snapshot version 更新。
- RLS：同 VFY；发版实际结果与目标侧 Evidence 语义不变，只做 Snapshot version 更新。

IMP 的跨 Authority 失败关闭顺序固定为：

1. Claim Provider 原子产生 `active` Claim、Artifact ID、Attempt 与不可复用 Revision Reservation；
2. Owner 以相同幂等上下文调用 Store `Artifact Allocate` / `Revision Allocate`；
3. Store 只有在 Revision Control Record 与 Canonical Blob 骨架提交并读回后才返回成功；
4. 读回与 Claim 不一致时不修改产品；若 Store 已建立 Revision，则先由 Store 将其准确终结为 `abandoned`；
5. 只有 Store 的终态读回成功后，Claim Provider 才可把匹配 Claim 改为 `abandoned`；任何一步失败时 Claim 保持 `active` 并继续锁定 Lineage / Resource；
6. Gate 通过后先 Store `Freeze`，再按既有条件调用 Claim Provider `complete`；Claim 完成失败时保留 Frozen Snapshot，并按现有 IMP 恢复规则处理。

该顺序不新增 Claim State、Artifact 字段或分布式事务要求。

### 7.2 Domain

16 份 Domain Spec 均未发现 Lifecycle Artifact 必须落到本地文件、Evidence 必须是文件路径、或通过目录发现 Artifact 的规则。它们的 `文件名` 是 Domain Spec / DSN Canonical Member Name；“路径、存储、持久化、Provider、主文件、Supporting Artifact”分别描述产品设计、DSN 父子语义或可选原生成员。

因此全部 Domain 只做 `version: "1.1"` 的 reference update，不改变任何模板、字段、Disposition、VFY Point 或 subordinate Gate。未来编制时如果某个 Domain 需要超出版本元数据的正文改动，必须视为矩阵偏差并停止审查，而不能以存储抽象为理由扩展业务语义。

## 8. Reference 与 Store Binding

### 8.1 Workspace 内 Reference

以下语法保持不变：

```text
<Artifact-ID>@<Revision>
<Artifact-ID>@<Revision>#<Item-ID>
<Artifact-ID>@<Revision>/<Member-ID>
```

短 Reference 由与 Project Boundary 一一绑定的 Workspace Authority Namespace 解析。它不携带 Provider、路径、数据库主键、对象 Key 或 endpoint，Store Promote 后不改写 Canonical Artifact 中的短 Reference。

### 8.2 Store Binding 的位置

Canonical Store Binding 至少包含：`workspace-id`、`store-instance-id`、Provider Profile、Authority Generation、Retention Policy、Binding State 与非秘密能力声明。

- Binding 属于 Resolver / Binding Authority 元数据，不进入 Canonical Artifact、CTX Front Matter 或任何领域字段；
- Runtime Workspace 可以保存 pointer / cache，但只有当前 Profile 定义的 Binding Authority 是权威；
- 单机 Provider 可使用本地排他 Binding record；共享 / 分布式 Provider 使用其协调机制；
- 无 Binding、多个 active Binding、Binding version 冲突或 cache 与 Authority 冲突时 fail closed。

### 8.3 跨 Store Artifact Locator

规范化语法固定为：

```text
sdlc-artifact://<store-instance-id>/<workspace-id>/<Artifact-ID>@<Revision>?generation=<N>&digest=sha256:<64hex>
```

- `store-instance-id` 与 `workspace-id` 是稳定、可编码的技术 ID；
- Revision 是不补零正整数；
- Query 参数顺序固定为 `generation` 后 `digest`；
- Locator 必须同时绑定 Store Instance、Workspace、Authority Generation、准确 Artifact Revision 和 Revision Package Digest；
- Locator 只用于跨 Workspace / Store transport、Export / Import、离线包与审计 Provenance；
- Locator 不是 Artifact Identity，也不能写入现有 Context / Artifact / Item / Member / Spec / Authority / VCS Reference 字段；
- 普通 URL、数据库主键、文件路径、Git branch / tag 或 Provider object key 都不能替代 Locator 或 Artifact Identity。

### 8.4 Export、Import、Promote

- Export 生成不可变包或 Projection，不改变 Authority；只有显式 `live-reference` lease 才延长 Source 生命周期；
- Import 校验身份、Revision、Canonical bytes、Members、摘要与 Contract 后只进入 staged non-authoritative namespace；
- Promote 默认以完整 Workspace Authority Namespace 为单位，以旧 Authority Generation 为前置条件原子切换 Binding；
- Promote 成功后目标是唯一可写 Authority，源变为 sealed / non-authoritative；失败时源继续是唯一 Authority，目标不得可写；
- 部分 Artifact Export / Import 不是 Promote，不能在另一个 Workspace 对相同短 Reference 声明 Authority；
- Provider 不可用、摘要不匹配、能力不足或 Retention 不满足时必须失败，不得切换到 temp、cache、filesystem、Git 分支或其他 Revision；
- 任一时刻不允许两个 Store 同时对同一 Workspace / Project Boundary Namespace 声明 Authority。

## 9. 最小语义与高级 Provider 能力分层

### 9.1 分层定义

- A：所有 Provider 必须提供的可观察语义；
- B：只有共享、分布式、远程或选择特定能力时才必须提供的协调机制；
- C：Provider Profile / Guide 中的实现建议，不属于领域 Contract。

| Mechanism | Layer | v1.1 约束 |
|---|---|---|
| Authority Generation | A | 所有 Canonical Binding 都有单调 Generation；写入、Freeze、Abandon、Promote 必须拒绝陈旧 Generation。单机实现可以只是本地原子 epoch |
| stale-writer rejection / conditional write | A | 所有 Provider 必须以 expected digest / generation 或等价 CAS 拒绝冲突；不得 last-write-wins |
| fencing token | B | 共享 filesystem、Git coordination、managed / remote 多 writer 场景必须能阻断旧 writer；temp / 单机 SQLite 可用本地锁 + Generation 满足同一可观察语义，无需分布式 fencing service |
| lease | B | 共享 Authority、长操作或明确需要 writer ownership 的 Profile 才要求；单 session temp 不强制 lease |
| Workspace Authority Registry | B | managed / remote 和多主机 Workspace 必需；单机 Profile 用本地 Binding Authority，不需要服务端 Registry |
| protected Git ref CAS | C | Git Provider 实现共享 Binding CAS 的推荐技术；具体 ref 名称、保护规则和 Git 命令留在 Git Provider Profile |
| retry-safe idempotency | A | 相同逻辑写入重试不得产生第二个 ID / Revision / Promote；结果必须可查询 |
| explicit idempotency key | B | remote / API 请求边界或无法依赖单一事务连接时必须提供；本地事务可用自然操作键实现等价语义 |
| live-reference lease | B | 只有 Provider / Export 声明支持 `live-reference` 时要求；不能保证 horizon 时必须拒绝该模式，可选择 self-contained archive 或 presentation |
| SQLite Schema、文件锁、journal、MCP/API、对象 Key | C | 只进入对应 Provider Profile / Guide，不得写入正式领域 Spec |

### 9.2 所有 Provider 的最小底线

无论 `temp`、单机 SQLite、filesystem、Git 或 remote，均必须保证：

- 单一 Canonical Authority；
- ID / Revision 不复用；
- 原子性或等价的可恢复提交边界；
- read-after-write 与原始字节 / SHA-256 读回；
- Exact Resolve 与递归 Input 验证；
- Frozen 不可变；
- 显式冲突和 fail closed；
- Retention 能覆盖已承诺 Reference 生命周期，不能满足时先 Promote 或停止。

temp 与单机 SQLite 不需要实现 Registry service、分布式 lease、受保护 Git ref 或远程 idempotency API；简单实现不能因此放弃上述可观察底线。

## 10. Canonical Serialization

v1.1 继续使用：

- YAML Front Matter；
- 完整 Markdown Canonical Blob；
- Supporting Members 原生格式；
- 主 Blob、每个 Member 的 SHA-256；
- 版本化、确定性计算的 Revision Package Digest；
- 可从 Canonical bytes 重建的查询、全文、Reference graph 与状态索引。

Revision Package Digest 是 Store / Projection 完整性元数据，只覆盖主 Blob digest 与按稳定 Member ID 排序的 Member digest 集合；它不替代 Control Input Digest、Check Set Result Digest、Manifest digest、Gate 或 Final Confirmation。

关系型表、SQLite Schema、JSON Projection 和搜索索引都不得成为 Canonical Artifact。若必须由结构化行取代 Markdown/YAML Authority，或无法无损 round-trip 字段、顺序、空值、Evidence 与摘要，则停止 v1.1 并转为 v2.0 候选。

## 11. Projection

| Projection | 用途 | Authority 边界 |
|---|---|---|
| downstream | Validator、Agent、索引器或执行器的结构化读取 / materialization | Consumer 必须验证 Source Reference 与 digest；Projection 不能登记为 Input Authority |
| human-review | Markdown、HTML、Office、Google Docs 或 UI 的评审与批注视图 | 编辑只产生候选 Change Set；Review View 不能被下游消费 |
| export | 归档、交换、发布目标或外部系统的包、文档、表格、Payload | 发布成功不改变 Canonical Authority；回流必须 Import |

每个 Projection 必须可读回：Source Locator、准确 Source Reference、Source Revision Package Digest、Source Evaluation Contract Set、生成时间、format / version、view digest、hidden mapping、mapping digest、Round-trip capability、最近 Import 状态和适用 Retention Mode。

- hidden mapping 只确定性映射 stable ID、章节、字段、表格行和 View element；不是安全边界；
- mapping 丢失、重复、损坏或不唯一时禁止猜测回写，View 降为 non-round-trippable Export；
- Source Generation、Source digest 或 mapping digest 不匹配，或 live Source 无法解析时，View 为 `stale`；
- Source 已有更高 Revision 时，旧 View 是准确 historical view，但相对 Lineage 为 `superseded`；
- Round-trip 必须由用户显式请求并具备准确 Workspace 写授权；
- Source 为同一 `open` Revision且 expected digest 匹配时条件写入，并使旧 Check、Gate 与 Final Confirmation 失效；
- Source 为 `frozen` 时，以其为 Base Revision 分配新的最大 `open` Revision，绝不修改 Frozen bytes；
- 无内容变化时报告 no-op，不创建空 Revision；冲突时停止，不自动 rebase、合并或选择其他 Revision；
- 编辑、保存、接受 Track Changes、解决评论或完成 Review UI 流程都不等于 Approval；
- Projection 永远不提供 Gate、Final Confirmation、Context、Input、Result 或下游 Authority。

## 12. Retention 与 temp Provider

| Policy | 适用范围 | 删除条件 | Promote 条件 |
|---|---|---|---|
| `session / ephemeral` | temp、单会话小任务 | session 结束，且无跨 session Reference、待保留 action / Evidence、未导入 Review edit 或下游义务 | 产生跨 session / downstream Reference、恢复、团队交接或正式 action Evidence 前 |
| `workspace / local persistent` | SQLite / filesystem 本地长期 Workspace | Workspace 明确关闭、全部 Reference obligation 结束、无未迁移 Authority，并满足本地 Policy 授权 | 进入多主机 / 团队、移除本地 Workspace 或 Reference 生命周期超过本地保证前 |
| `managed / shared` | remote / managed 团队与集中治理 | 满足服务、团队、法规、Reference closure、归档 / 迁移和授权要求后 | 更换服务、租户或治理边界时按完整 Workspace Promote |

删除规则：

- 仍被保留中的 Context、Input、Item、Member、Evidence、Authority 或有效 `live-reference` horizon 引用的 Frozen Revision 不得删除或静默不可解析；
- Projection / cache 可重建，但含未 Import 的人工编辑时必须先导出 Change Set 或获得放弃决定；
- `open` / `abandoned` 只有在没有外部 Reference、正式 action / effect Evidence 保留义务且 Policy 允许时才可清理；Lineage 保留时编号与终态不可复用；
- self-contained archive 与 presentation 不 pin Source；live-reference 必须有明确 horizon / lease；
- temp Reference 的有效范围不得超过声明 session / process；session 结束前存在持久义务时必须 Promote；
- 删除、过期或 Workspace retire 必须返回明确 `retention_expired / workspace_retired / non-authoritative`，不得由 cache 或其他 Store 补位；
- 数据完成后是否继续保留由 Retention Policy 决定，本 Spec 不要求所有需求和 Artifact 永久保存。

## 13. v1.0 兼容与迁移

### 13.1 filesystem 映射

现有 `artifacts/000-ctx/` 与 `artifacts/100-req/` 至 `artifacts/600-rls/` 映射为 legacy filesystem Provider Profile：

- Artifact 前缀 / Phase 目录只用于 legacy profile 的物理查找；
- `<Artifact-ID>/revision-index.md` 映射为逻辑 Revision Control Record；
- `revisions/<NNNNNN>/<Artifact-ID>.md` 映射为 Canonical Blob；
- 同一 Revision 目录中的其他文件映射为 Supporting Members；
- 目录、文件名和补零格式不是 Artifact Identity，不能被其他 Provider 继承为强制物理布局。

精确路径表、文件锁、atomic rename、journal 和恢复命令属于 filesystem Provider Profile / Guide，不进入领域 Contract。

### 13.2 挂载、Import 与 Promote

- v1.0 Frozen Workspace 可以作为只读 filesystem Authority 挂载；Resolver 必须继续按其原 `Evaluation Contract Set` 验证；
- 导入 v1.1 Store 时保留原始 Canonical bytes、Artifact ID、Revision、State、Supporting Member bytes 和现有摘要，不重写 Front Matter、Status、Gate 或 Contract Set；
- Store 可以在外层新增 Revision Package Digest、Authority Generation 和 staged import metadata，但这些不写入旧 Canonical Artifact；
- Import 不改变 Authority；只有完整 Workspace Promote 可以改变 Canonical Store；
- 原 v1.0 Source 在 Promote 成功前保持唯一 Authority；成功后封存为 non-authoritative archive；
- 不允许复制后让 filesystem 与 SQLite / remote 同时可写或同时声明同一短 Reference 的 Authority。

### 13.3 Migration Manifest

需要 Store-owned、非 Canonical 的 migration manifest。它至少记录：

- Source / Target Store Instance 与 Workspace ID；
- Source Authority Generation 与 Contract Snapshot；
- Artifact / Revision / State / Member inventory；
- 原始 Blob、Member 与 Package digest；
- 每项 Import 校验结果、失败原因和 staged 状态；
- Promote 前置条件、结果与新 Authority Generation；
- Source sealed / retained / deleted 处置。

该 manifest 是迁移控制记录，不是 Lifecycle Artifact、Supporting Member、Gate 或新的领域字段。

### 13.4 迁移失败

- 任一身份、Revision、State、Reference、成员、摘要或兼容性校验失败时，Import / Promote 失败；
- 目标 staged copy 保持 non-authoritative 或按 Provider 事务回滚；
- Source 保持唯一 Authority；
- 不允许部分 Workspace 获得 Authority，不允许 fallback 到未验证副本；
- v1.0 Frozen Snapshot 绝不原地改写，修复只能通过源 Contract 允许的新 Revision，或在 v1.1 Authority 建立后按 v1.1 创建新 Revision。
